## What the owner asked for
A minimal plugin, tonight: take a realistic Niagara effect (above all **Niagara Fluids**: gas fire, smoke, explosion) and produce a pixel-art version in the game's palette that is far cheaper at runtime, and that keeps its **lighting behavior** in a ray-traced / Lumen scene (he said "ray tracing behaviors": I read it as: the baked effect still lights the scene, casts shadows through a real light, and shows in reflections). It must not be a plain "pixelate" filter.

## The plan

### Plugin layout: `Glyphbound/Plugins/GBPixelVfx/`
- `GBPixelVfx.uplugin` with `"EnabledByDefault": false` while it is being written (another chat builds the same project tonight; a half-written plugin must not break its builds). My builds pass UBT `-EnablePlugin=GBPixelVfx`; my runs pass `-EnablePlugins=GBPixelVfx,NiagaraFluids`. At the end the plugin gets an `"Enabled": true` entry in `Glyphbound.uproject`. NiagaraFluids is never enabled in the .uproject: only on the bake command line, so the packaged game does not carry it.
- Module `GBPixelVfx` (Type `Runtime`): no Niagara dependency.
  - Clip = `Content/Data/Vfx/<Id>.png` (atlas) + `<Id>.json` (frame size, columns, frame count, fps, loop, world size in cm, pivot, per-frame light track: intensity 0..1, color). `Content/Data` is already staged as loose files (`DirectoriesToAlwaysStageAsNonUFS`), and it is the only part of `Content/` in git.
  - `UGBPixelVfxSubsystem` (GameInstanceSubsystem): loads a clip on first use: PNG through `IImageWrapper` into a transient `UTexture2D` (PF_B8G8R8A8, sRGB, `TF_Nearest`, no mips, clamp), cached.
  - `UGBPixelVfxComponent` (USceneComponent): creates a `UStaticMeshComponent` with `/Engine/BasicShapes/Plane` and a dynamic instance of a generated material `/Game/Glyphbound/Materials/M_PixelVfxSprite` (Masked, Unlit, two-sided; params `Atlas` texture object sampled with "from texture asset" sampler, `FrameRect` vector = UV offset.xy + scale.zw, `Tint`, `Glow`; emissive = color * (1 + Glow)). Facing modes: full billboard to the camera, upright (yaw only), flat on the ground, fixed. Stepped playback at the clip fps, loop or one-shot (auto destroy). Also owns a `UPointLightComponent` driven every frame by the clip's light track (intensity, color, attenuation radius; options: cast shadows, affect indirect/Lumen), and sets the quad `bVisibleInRayTracing` / visible in reflection captures. That light is how the baked effect keeps the "lighting behavior": shadows, GI and reflections of the light are computed by Lumen (hardware RT when enabled).
  - The material is generated by a Python script in the plugin (same pattern as `Tools/Jam/make_materials.py`) into `/Game/Glyphbound/Materials`, which is already in `DirectoriesToAlwaysCook`.
- Module `GBPixelVfxBaker` (Type `UncookedOnly`): depends on `Niagara`, `GBPixelVfx`, `ImageWrapper`, `Json`.
  - Bake jobs are JSON files in git: `Glyphbound/Plugins/GBPixelVfx/Bake/Jobs/<Id>.json` (Niagara system path, user parameter overrides, capture camera, timing, pixel settings, palette ramps, light settings).
  - Bake runs in an uncooked game process without a window, the same way the smoke test runs:
    `UnrealEditor.exe Glyphbound.uproject /Engine/Maps/Entry?game=/Script/GBPixelVfxBaker.GBPixelVfxBakeGameMode -game -RenderOffscreen -windowed -ResX=640 -ResY=360 -unattended -nosplash -nosound -EnablePlugins=GBPixelVfx,NiagaraFluids -PvfxBake=All`
  - `AGBPixelVfxBakeGameMode` (no pawn, no HUD): on BeginPlay sets `FApp::SetUseFixedTimeStep(true)` / `SetFixedDeltaTime(1/SimFps)`, then for each job: spawns an actor with a `UNiagaraComponent` (the system loaded by path, e.g. `/NiagaraFluids/Templates/Gas/3D/Systems/Grid3D_Gas_Fire`), applies user parameters, optional key light from the top left (style guide), a `USceneCaptureComponent2D` (orthographic, `PRM_UseShowOnlyList` with the Niagara component, `SCS_SceneColorHDR` so A = inverse opacity, render target RTF_RGBA16f at e.g. 512x512, `bCaptureEveryFrame=false`, `CaptureScene()` by hand), waits the warm-up, then every k-th simulation frame captures and reads back with `FTextureRenderTargetResource::ReadLinearColorPixels` (blocking is fine).
  - CPU conversion (pure functions, unit-tested): exposure + tone map; area downsample to the frame size (e.g. 48x64) in premultiplied linear space; alpha = max(1 - invOpacity, luminance key for additive effects); hard alpha threshold (style guide: alpha is 0 or 255); color to the job's palette ramps (mode "Ramp": normalized luminance -> index in one ramp; mode "Nearest": nearest color in OKLab among the listed ramps), luminance normalized by the clip's 99th percentile; temporal hysteresis (keep last frame's index when the value is within a margin of the band edge) to stop flicker; remove islands smaller than N pixels and fill 1-pixel holes; optional 1 px outline (black or the ramp's darkest); optional loop cross-blend of the last frames into the first (before quantization); light track per frame = coverage-weighted emissive luminance, normalized, color from the job.
  - Output: `Content/Data/Vfx/<Id>.png` + `<Id>.json`, plus review files in `Saved/PixelVfx/<Id>/` (contact sheet upscaled x6 nearest, the unconverted source frames strip).
  - A second mode `-PvfxCompare=<Id>`: spawns N instances of the source system, measures average frame time over 120 frames, then N instances of the baked clip, measures again, logs both (the "it is lighter" number), and saves one side-by-side screenshot.

## Questions
1. **Fluids in a scene capture.** Niagara Fluids gas grids are GPU simulations rendered by a ray-marched volume material on a mesh. In a `-game -RenderOffscreen` process, will `USceneCaptureComponent2D::CaptureScene()` with `PRM_UseShowOnlyList` (ShowOnlyComponent = the NiagaraComponent) render them, lit, with A = inverse opacity in `SCS_SceneColorHDR`? Does the GPU sim tick normally (once per frame) when a scene capture is also rendered in that frame, or can the capture cause double ticks / no ticks? Is there a known problem with fluid templates under an orthographic capture (the raymarch material uses the camera position)? If orthographic is risky, say so and I will use a long-lens perspective camera.
2. **Fixed time step.** Is `FApp::SetUseFixedTimeStep(true)` + `FApp::SetFixedDeltaTime()` from a GameMode's BeginPlay enough in `-game`, or should the command line carry `-UseFixedTimeStep -FPS=60` / `-benchmark`? Anything else needed for a deterministic bake (Niagara `SetSeekDelta`, `r.Niagara...`)?
3. **UncookedOnly module with a GameMode chosen by URL** (`?game=/Script/GBPixelVfxBaker.GBPixelVfxBakeGameMode`) in `UnrealEditor.exe -game`: does the module load early enough for the class to resolve? Should its LoadingPhase be `Default` or earlier? Will packaging (`RunUAT BuildCookRun`, Development, Win64) ignore the UncookedOnly module cleanly?
4. **Plugin isolation.** `"EnabledByDefault": false` + UBT `-EnablePlugin=GBPixelVfx` (TargetRules.cs has `[CommandLine("-EnablePlugin=", ListSeparator = '+')]`) + runtime `-EnablePlugins=GBPixelVfx,NiagaraFluids` (PluginManager.cpp `ParsePluginsList(TEXT("EnablePlugins="))`): does this build and load the plugin modules without touching the .uproject? Any trap (the Editor refusing a plugin whose binaries were built for a different target receipt, NiagaraFluids needing shaders compiled on first use, its `/NiagaraFluids/` mount point)?
5. **Alpha.** Is "A = inverse opacity" of `SCS_SceneColorHDR` reliable for translucent volume materials and for additive emissive? Would you rather render twice (black and white backdrop) and difference-matte? Which is cheaper to get right tonight?
6. **Lighting behavior at runtime.** Is the quad (Masked Unlit emissive, static mesh, movable) + a movable point light driven by a baked light track the right minimal answer for "it still behaves under Lumen / ray tracing"? The project today has Lumen GI and reflections on (`r.DynamicGlobalIlluminationMethod=1`, `r.ReflectionMethod=1`), hardware ray tracing NOT enabled (`r.RayTracing` unset), DX12 SM6, the dev machine is an RTX 4080 laptop. Should I (a) leave the project config alone and only show a hardware-RT run of my demo through a command-line override (which exact override works for the startup-only `r.RayTracing`?), or (b) enable hardware RT project-wide two days before the deadline? I lean to (a). Also: any cheap, real improvement here (e.g. is an Unlit emissive masked quad visible to Lumen reflections / hit lighting; should the material be Default Lit with emissive instead)?
7. **Pixel conversion.** Anything in the conversion list that will look bad on fire/smoke at 48x64 and 12 fps, or an obvious missing step? Keep it to what matters tonight.
8. **Anything else** that will cost me an hour if I do not know it now (API that changed in 5.9, a readback that returns black offscreen, show-only lists ignoring Niagara mesh renderers, transient textures from PNG in a packaged build, `IImageWrapper` module name, etc.).
