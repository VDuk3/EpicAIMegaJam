**Where the AI failed and how we fixed it** (the part judges value most in a dev log)
- **The first maps had no sense of place.** A planner (Claude Fable 5.2, High, 46 minutes) drew both eras on one grid with routes, portals, cover and spawn points, and checked its own layout with a script. A builder script made the greybox, and a dressing script fitted 374 kit meshes into the rectangles the plan gave them, each by a rule (turn to the long side, tile, stack). The self-review looked for gaps, z-fighting and collision, and missed the only thing that mattered: no room had been described as a place, and no piece was there because the room needed it. The owner rejected both maps; they, the plan and the scripts were deleted (`c04f05e`). **Fix:** a new rule for every map since: describe the space as a place first (what it is, who built it, what for, what it looks like), and an asset goes in only because that description asks for it; plan with the owner step by step. The future base was built that way the same night.
- **"I can't get past the start."** The dressing script turned collision off with `set_collision_enabled`, but a named collision profile re-applies its own settings when the map loads, so all 374 dressing meshes still blocked, and the kit door piece's single collision hull closed the first doorway. The navmesh smoke passed anyway, because dressing meshes do not affect navigation. **Fix:** the `NoCollision` profile, and a new check that sweeps the player's own capsule from the start through the doorway and names what blocks it. It was seen failing (with the door's collision put back) before it was trusted.
- **Muse Spark defended a wrong theory for forty runs.** On the plugin's second batch it made 53 showcase runs in 2 h 45 min, concluded that the engine's Plane mesh "does not rasterize in `-game`", swapped it for a 1 m cube and stopped moving the camera. Muse also exited without writing anything on the site's code later that day. After each stall the work went to a Claude Sonnet 5.5 subagent, as the owner allowed.

Only the scripted run on the packaged exe saw it (six failed Entity checks). One line in `DefaultGame.ini`. It also meant that day 1's last package very likely had the placeholder boss: day 1's entry was corrected (`39f27b8`).
- **A camera effect that was never visible.** The climb's camera dip did nothing: the camera follows the control rotation, and the engine overwrites the camera's rotation on every view. That means the "view shake" on spell interrupts, added on day 1, had never been visible either. Now both go through the camera's additive offset.
- **Tests that pass wrong code, again.** The project rule says every test must be able to fail. Sol still found six such tests in the plugin's first batch, seven in its second, and more in the ledge climb (a "hands never show" or "teleport across" implementation would have passed). Each was rewritten with hand-calculated expectations; on the plugin, the implementer reverted one fix to see its test go red.

## First block: GBPixelVfx, a plugin that turns Niagara Fluids into pixel art (06:15 to 13:12)
Detail: [`2026-11-13_pixelvfx_block.md`](2026-11-13_pixelvfx_block.md). Architect: Claude Fable 5.2.

**The owner's idea and the first answer.** The owner asked (Spanish) for "a plugin that converts Niagara and Niagara Fluids to pixel art [...] not a plain pixelation of the original effect; the modern parameters of a Niagara Fluid carried over to a pixel version that behaves exactly the same but looks like pixel art and is light". The architect said no to the general converter and yes to a small one: "behaves exactly the same and is light" contradicts itself, because what costs in a fluid is the simulation, not the drawing; and there is no general translation of parameters, since every Niagara system is a different graph. The strong half of the idea is the other one: fire, smoke and explosions are hard to draw by hand, and the game's art rule says all magic is pixel art. The owner: *"hagamos la versión mínima que sugieres. Eres el arquitecto. [...] Me voy a dormir, no te detengas a pedirme permisos ni a hacerme preguntas. Este plugin es TUYO"* ("let's do the minimal version you suggest. You are the architect. [...] I am going to sleep, do not stop to ask me for permission or questions. This plugin is YOURS"). He added that what interests him most is "Niagara Fluids and ray tracing behaviors"; the architect read the second part as "the pixel version still lights the scene, casts shadows and shows in reflections", and logged it as an interpretation to confirm.

**What it is.** A bake runs the real simulation in a windowless `-game` process with its own game mode, captures it through a long-lens perspective camera, and converts each frame on the CPU to the master palette's ramps with hard alpha, stepped at 12 fps with hysteresis against flicker. Each clip is a few-kilobyte PNG plus a JSON file in `Content/Data/Vfx` (loose, like all our data). At runtime the clip plays on a camera-facing quad and drives **a real point light** from a light track baked with it. Two modules: the runtime one has no Niagara dependency; the baker is Editor-only and Niagara Fluids is enabled only on its command line.

**Who did what, in order.**
1. Plan and four bake jobs (fire, smoke, explosion, arcane fire) by the architect; plan review by **Astra** (8 notes, above).
2. **Muse Spark**, first batch (06:33 to 08:20): both modules, the bake, the conversion, nine tests, the material script. The bake worked end to end (four clips in about 50 s). Then it spent half an hour on black showcase screenshots and one run hung the GPU; the architect stopped it.
3. The architect looked at every sheet and fixed four looks through the job files, not code (the fire was mostly dark red; Epic's "smoke" template is a smoke column with fire at its base, so it got a hot and a cold ramp; the ColoredFire template rendered nothing, so the arcane clip is the fire simulation on the arcane ramp).
4. **Sol, first review:** 18 findings, all accepted (the pivot offset applied in the wrong space, state set only when the quad was first created, a failed job skipping the next one, six tests that wrong code would pass).
5. **Muse Spark, second batch** (08:24 to 11:10): the 18 findings and new features, then the 53-run stall described above. The architect found the real cause.
6. **Sol, second review:** 12 findings (the quad inherits its actor's scale but the pivot math did not; the fade-out's last frame was not empty), fixed by a **Claude Sonnet 5.5 subagent** in eight minutes.
7. Into the game (architect): plugin enabled, a smoke step, then the **Fireball** flies with the baked fire (owner: *"Fireball con fuego"*). The architect also put the baked explosion on its impact; the owner cut it (*"Quítala"*). The smoke step now fails if an impact clip comes back by accident. Seen on the way: the sprite material's glow bleached the smoke to light grey; the glow now applies only to fire-like pixels.

**Results.** 15 tests of the conversion. Four clips baked in 51 s; the four PNGs together are 56 KB. Side by side at 1280 x 720: **8 live simulations cost 50.1 ms per frame, 8 baked clips with their lights 4.5 ms** (the empty stage 4.1 ms). The same stage also runs with hardware ray tracing through a command-line override (`r.RayTracing=1`, `r.Lumen.HardwareRayTracing=1`, `r.SkinCache.CompileShaders=1`); the project's settings were not changed. Two script lessons: `$PSScriptRoot` is empty in a `param` default when the script has `[Parameter()]` attributes, and an `-ini:` override needs the `[Section]` prefix on every key, or only the first key applies.

**Packaging.** The first package (277.3 MB) proved the one thing no Editor run could: the cooked game finds the plugin's materials and the loose clips. The same run found the Entity's missing cook folder; the second package was **299.7 MB** (`6062d97`).

## Design decisions
All by the architects unless marked "owner". Provisional values are marked in the GDD (v0.35 to v0.49, all on this date).
- **A small pixel-VFX plugin, not a general converter.** "Behaves exactly the same and is light" cannot both be true: the cost is the simulation. Baked clips look like the fluid in motion, cost about a hundredth, and no longer react. Owner agreed.
- **Our own capture, not the engine's Niagara Baker.** The Baker's renderer is in private Editor headers a plugin cannot link, and it stops at a smooth flipbook; the pixel conversion is the point.
- **A real light per clip, not emissive pixels.** A small moving quad does not reliably light a Lumen scene; a light gives shadows, GI and reflections. Named honestly as a stylized approximation of the volume's light.
- **Hardware ray tracing not enabled in the project.** Two days before the deadline it would touch every system and every player without RT hardware; the demo uses a command-line override.
- **HUD still on the canvas, no UMG; our own pixel font; the engine's Roboto for cyberpunk.** Everything stays C++ and text in git, nothing to license, import or cook.
- **Shared menus follow the era; skill pages follow their tree; the in-game HUD follows the held item** (owner, v0.39).
- **E, not W, for the second skill page.** W already means "up" in every menu.
- **Perks per gun (owner), then the three general perks back (owner), then three new perks (owner) with Extended Tube at +1** (architect, confirmed by the owner). Every change was checked against encounter lengths; the Entity's phases went to 7,300 health.
- **Element choice before the QTE's key sequence, on fixed keys, with its own clock** (owner: fixed places; architect: the separate clock, so choosing never costs QTE time).
- **The ledge climb in first person with existing art only;** first "must face the wall", then (owner) any direction by intent.
- **Plugins enabled only where a real asset needs them**, measured by a module scan.
- **The Fab packs' files are never fed to our generators** (every listing forbids AI training).
- **Maps: the place first, then the pieces** (after the owner's rejection). The kits' demo maps are used as their authors assembled them for the shells, our level design goes inside, and every walk the owner makes is a round of notes.
- **Kit pieces collide exactly as they look** (complex collision as simple): their simple hulls close doorways.
- **A third party's picture inside a free model is replaced by our own** (brand and license risk).
- **Every first-person hand at 4 px per art pixel** (480 x 270), to keep the approved staff hand as it is.
- **Exceptions to "the implementer is Muse Spark", with the reason.** UI, poses and level work were done by the architects directly, because they were judged screenshot by screenshot and a brief per round would cost more than the change (HUD, shotgun poses, skill tabs, hub, perks, menu transition, enchant choice, the ledge climb's review fixes, the maps, the corridor). After Muse's stalls, a Claude Sonnet 5.5 subagent took the plugin's second review and the site's code (allowed by the owner). The world planner was a Claude Fable 5.2 subagent at the owner's request.

## Problems and solutions
- **Several AI chats sharing one machine and one checkout.** One build, run or package at a time per machine is a project rule. Solved with a lock file the scripts check and messages between chats when it is taken and freed; commits name their paths, and once were written straight into the git index to leave another chat's work out.
- **The package went over the 1 GB limit** with the future base (1,206 to 1,445 MB; the High Tech Base textures alone cook to 1,655 MB at 4096 px). The owner set the limit aside for now; the texture cap is half done and must be finished before submission.
- **The ASSETS share stopped syncing** (a VPN on that PC). Reconnected with the person typing the password.
- **The Editor's MCP connection was down in one chat** (the Editor started after the chat). The architect wrote `Tools/Jam/mcp_call.js` to call the MCP server over HTTP from a script.
- **The crashed Editor's log** could not be collected by `Stop-EditorMcp.ps1` (no process left); collected by hand with `Collect-UnrealAgentLog.ps1`, as the dev log rules ask.
- **A UE 5.9 change breaks one Fab effect:** Medieval Kingdom's shore foam reads `WaterZone.WaterInfoTexture`, which no longer exists. Only that effect; to fix or drop if the castle's water is used.
- **Corrections to day 1's entry made today:** the shotgun package's placeholder boss (`39f27b8`), ASSETS' pistol trace (`9159cca`), the credit for the pistol's third-party concept reference (`35f4b45`), and the shotgun's reference image made with Tripo (`05cdffd`).
