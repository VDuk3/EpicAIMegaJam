**What the AI did well**
- **Contracts before code.** The architect wrote every public header first, with the specification in the comments, and checked that they pass Unreal's header tool. Ten implementers then worked at the same time without seeing each other's code. Result of the first full compile: 3 errors in 17,500 lines (two name collisions between files that Unreal compiles together, one local variable hiding an engine member).
- **Implementers reported their own doubts.** Each one ended with a list of what it could not verify and what it needed from the others. Those lists became the checklist of the integration pass.
- **The reviewer found design-level bugs, not typos.** Example: dying restored the inventory from the checkpoint while opened chests stayed open, so a death could delete rewards for good. The fix was a design decision (death now keeps everything collected), taken by the architect and written into the GDD.

**Where the AI failed and how we fixed it** (the part judges value most in a dev log)
- **The game compiled, passed its tests, passed review, and had no floor.** The game mode builds the test arena "when the map has no player start"; the engine's empty map has one. So the player spawned in the void and fell forever. No compiler, no unit test and neither reviewing model caught it. It was caught by `gb.Smoke`, a console command the architect wrote because AI agents are not allowed to run Play In Editor here: it runs the game by itself, uses the main systems on a timer, logs what happens, takes screenshots and quits. The first run printed the player's height: -1,140 cm, then -10,992 cm. The script now fails when the player falls or the level has no enemies.
- **Magenta hands.** The placeholder sprites are text: rows of letters and a palette. The implementer used `s` for skin and `S` for shadow. Unreal's string keys ignore case, so one of the two colors was lost and those pixels were drawn in the "missing" color. Seen only in the screenshots. Fixed with a script that renames colliding keys to digits; the rule is now in the data header.
- **Works in the Editor, breaks in the package.** The arena code called `ADirectionalLight::GetComponent()`, which only exists in Editor builds. The Editor build was green; the first packaging failed. Fixed, and the game target is now built on every integration, not only when packaging.
- **The plugin diet broke the package.** Among the 103 default plugins the architect turned off was Cascade, the old particle system, which the game does not use. The engine's own renderer settings still look up two console variables that only that plugin registers; the Editor shrugs, but the cook counts the two log errors and fails. Cascade is back on (102 plugins off), with the reason written next to the list in `Tools/Jam/trim_plugins.js`. Lesson: "the game does not use it" is not the same as "the engine does not need it", and only packaging tells.
- **The architect's own slip:** a "commit everything" swept two files that the integration agent was still editing into a commit labeled as a design change. Harmless, but the history is slightly mislabeled there (`1fad33f`). Since then, commits made while an agent is working name their paths.
- **A measurement that showed nothing.** See "Problems".

## Seventh block: elemental build-up (Ignite, Shock, Frost)
The owner wrote a full spec (in Spanish; verbatim in `Prompts/feedback8_elemental_spec_owner.md`): every enemy builds up fire, lightning and ice separately; a full bar starts a status (Ignite = damage over time, Shock = interruption, Frost = freeze or strong slow), with per-enemy resistances, thresholds, durations, immunity and reactions, per-spell and per-weapon build-up, a weak-point bonus, everything in data, events for future visuals, and a list of 13 checks. It ended with "if you have any questions, ask them before continuing".

The architect read the combat code first and reported the conflicts instead of building on top of them:
- Every elemental hit already applied a small effect: fire hits burned (a damage-over-time), lightning hits applied a 40% slow **already named "Shock"**, the ice enchant chilled. Adding Ignite on top would have meant two damage-over-time systems and two meanings of "Shock".
- Slows multiplied (ice floor 50% x chill 30% = 65%), against the spec's "Frost must not stack uncontrollably with the ice floor".
- There were no elemental resistances at all, only a general damage-taken multiplier.
- In this game the weapon enchant works on guns only; the elemental sword and the ember staff have elements of their own.

It asked two design questions (and decided every engineering question itself, as the owner asked). Translated from Spanish:
1. "What do we do with the existing per-hit effects?" Owner: **remove them all**; the bar's status is the only elemental effect (the ice floor keeps its zone slow).
2. "Should the elemental sword and the ember staff build up too?" Owner: **yes, both**.

| Part of the spec | How it was built |
|---|---|
| Three independent bars per enemy, threshold, decay after a delay, reset on trigger, no build-up while active, immunity after | A pure, tested struct (`FGBBuildUpMeter`) with three phases (building, active, immune). Decay is computed from elapsed time, so one 1 s step equals ten 0.1 s steps (tested). One small component per enemy (`UGBElementalStatusComponent`) holds three meters and only ticks while a bar is not empty, 10 times a second: an idle horde costs nothing. |
| No duplicate build-up from one hit, explosions, piercing shots, shotguns | Every hit carries an event id: one per shot, cast, blast or tick. Each enemy remembers its last 8 ids, and a repeated id only adds the part above what it already added. The eight pellets of a shotgun shot give one build-up, and the best pellet counts (a head pellet after a body pellet adds only the difference). Tested. |
| Reuse the existing damage events | Build-up rides on the one damage function (`DealDamage`). The flamethrower's 0.3 s ticks, the fire wall's and the orb's ticks, the rune's blast and the fireball's explosion needed no change at all. Only the ice floor, which deals no damage, sends its build-up directly from its existing tick. |
| Per-enemy configuration, damage and build-up resistances separate, defaults only as fallback | Plain enemy stats in `Enemies.json` (`FireDamageTaken`, `FireBuildUpTaken`, `FireBuildUpThreshold`, `LightningStatusReaction`...), read through the existing stat system, so perks can modify them later. A value an enemy does not set falls back to `Game.json` `ElementalDefault.*`. The brute only gets interrupted by Shock and only slowed by Frost; the armored orc is weak to lightning. |
| Ignite must not duplicate Fireball's burn | The burn is gone (owner's answer). Ignite reuses the existing status effect system for its damage ticks, so there is one damage-over-time system. |
| Shock: discharge, interrupt, stun, or immune; Frost: freeze or strong slow | A Shock discharge is a small hit of lightning damage. Stun and freeze pause the enemy's state machine (its attack timers stop too); interrupt cancels only the attack being wound up. The reaction is an enemy string; "None" makes it immune to the status but not to the damage. |
| Frost and ice floor slows must not stack | A new modifier operation, `MultiplyMin`: among those on a stat, only the strongest counts. The ice floor's 50%, Deep Freeze's 55/60/65% and its 80% cap are unchanged (tested). |
| Weak-point bonus once, without touching the head damage bonus | The weak-point check was split out of the damage bonus (`IsWeakPointHit`), the single place to add non-head weak points later. A hit is either on a weak point or not, so the bonus cannot apply twice. |
| Events for visuals, no universal indicator | The component broadcasts "build-up changed", "status started" and "status ended" for each enemy's future look. For testing only: `gb.ShowElemental 1` prints the bars over enemies, and `gb.BuildUp Fire 30` adds build-up to nearby enemies. |

## Eighth block: guns are less accurate while moving
Owner's note (in Spanish, translated): "I'd like shot accuracy to be lower while moving than while standing still."

- Architect's design (GDD v0.23, numbers provisional): each gun gets two new stats, `MoveSpread` (hip) and `AimMoveSpread` (aiming), extra degrees of spread at full walk speed. The bonus scales with horizontal speed over the current max walk speed, clamped to 0..1, so aiming (which already slows the walk) still costs some accuracy at a slow aimed walk. Pistol 1.2 -> 3.7 hip, rifle 1.8 -> 4.8, shotgun 6 -> 9.
- One function (`AGBGun::GetCurrentSpread`) feeds both the shots and the crosshair, so what the player sees is what the gun does.

## Design decisions
All taken by the architect; the owner asked not to be consulted on engineering. The provisional gameplay rules and numbers that had to be invented are listed in GDD section 18 for the owner to confirm or change.

- **C++ only, built from the blank template.** The first-person template was not used: the jam asks for gameplay beyond Epic's templates, and AI agents handle C++ text far better than Blueprint graphs.
- **No Gameplay Ability System.** Considered (the GDD lists it as a candidate) and rejected: heavy boilerplate and asset setup for a 4-day jam. Replaced by three small pieces we fully control: one stat system (base value from data + stacked modifiers), one damage function, one status-effect component. Skill-tree nodes, armor, slows, potions, air passives and the weapon enchant are all "a named group of modifiers".
- **All gameplay numbers in JSON under `Content/Data`, shipped as loose files.** Git only carries text in this team, AI agents edit text reliably, and the owner can retune a packaged build with a text editor. `gb.ReloadData` reloads while playing.
- **Spells = data + a behavior class.** Each parameter has `Base / Min / Max / ScaledBy` (none, QTE power, QTE reach). Eight behaviors cover the nine active spells and the enchant; a new spell that fits a behavior is one JSON entry.
- **No binary assets needed to run.** The test arena, input actions and placeholders are built in C++; placeholder pixel art is rows of text turned into textures at runtime. The whole game is reviewable as text in git.
- **HUD drawn with the canvas, not widgets.** The two skins (90s RPG with the staff, cyberpunk with a gun) are two style structs.
- **Death keeps what was collected** (after the review): back to the checkpoint's place with full health, mana and ammo; nothing owned is rolled back.
- **Modifier keys by weapon type** (`Weapon.Gun.*`), added after the review found the gun enchant also buffed the staff.
- **Routing of work between models** (owner's rule): parallel work to Claude subagents, one-batch-at-a-time work to Muse Spark, reviews to Codex.
- **Exceptions to "the implementer is Muse Spark"**, with the reason: the project scaffold, the header contracts and the build / test / smoke scripts were written by the architect directly (they are the architecture and its verification); two one-line fixes and the sprite palette script were also direct (smaller than the prompt that would describe them).

## Problems and solutions
- **Trimming plugins did not speed up a warm Editor boot.** We expected a gain; measured, there is none worth the name. Mounted plugins went from 315 to 160, warm boot stayed around 10-11 s. The cost of a warm boot is not in the plugin count. We keep the trimmed list (fewer modules to load and cook) and spent no more time on it.
- **Screenshots arrive late.** The engine captures a screenshot a few frames after the request, so in the first smoke run a shot of "the future" showed the inventory that opened right after. The script now leaves a full second after each shot.
- Everything else is in "Where the AI failed" above.
